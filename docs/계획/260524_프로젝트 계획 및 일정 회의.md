# 계획 수립

각 단계별로 바이브코딩 vs. 프로세스 결과를 비교해보자.

### 요구사항 분석

1. 바이브코딩 - “쇼핑몰 만들건데, 요구사항 뽑아줘” 
2. 프로세스 - 사람이 직접 요구사항 뽑기

비교 방법: 요구 품질(모호성, 원자성 등) 에 입각하여 판단 비교

### 설계

1. 바이브코딩 - 없음
2. 프로세스
    1. 다이어그램(유스케이스/클래스/시퀀스(?))
    2. 컴포넌트/모듈 설계 → 클래스다이어그램을 그리면서 고려…

비교 방법: 응집력, 결합도를 바이브코딩하면 안좋을 거 같으니

### 구현 - 코딩 자체는 둘다 LLM한테

1. 바이브코딩
    1. 모듈 단위도 없고, 다이어그램도 없고, 요구사항대로 만들어줘
    2. 또는그냥 쇼핑몰 만들어줘 프롬프팅할 것
2. 프로세스 - 설계 뽑힌 것들을 바탕으로 만들어줘.

비교 방법: 설계유무에 따른 구현 결과를 비교하자 → 어떻게?

- 비용 - llm 토큰
    - 설계 없이 원하는 결과물이 나올 때까지 계속 자연어로 설명하면, 토큰이 많이 쓸거 같아서.
    - “원하는 결과물” 이란? 설계 시 나온 기능/비기능 충족도.
    - 바이브코딩에서는 요구사항을 뽑지 말고, 일단 구현을 먼저 시킨다음에, 우리가 적은 요구사항과 비교해서 없는 기능을 계속해서 자연어로 설명하면서 하나씩 추가하는 방식으로 가보기.
    - 바이브코딩: 요구사항을 하나씩 말할 때마다 토큰 얼마 썼는지를 측정해보는거다.
- 속도 - 결과물이 나오는 속도
    - 바이브코딩 - 원하는 결과물이 나올 때까지 몇번의 프롬프팅을 했는가. 시간이 얼마나 걸렸는가
    - 프로세스 -  요구사항 & 설계 후 → 원하는 결과물에 도달하기 까지 얼만큼 수정을 하는지 (수정횟수 & 토큰)
- 결합도, 응집도 차이 비교
    - 코드를 봐야할 것 같은데 → inspection을 해서 우리가 직접 판단했다.

### 테스트

1. 테스트케이스를 너가 뽑아
2. 우리가 직접 테스트 케이스 뽑기

비교 방법: 테스트 케이스 뽑힌 것 비교하기 - 얼마나 정교하게 뽑히나? (이것도 다 기준이 있었던 것 같음 - 강의록 / 책 찾아보기)

### 유지보수

수정사항이 생기면, 얼마나 효율적으로 수정하는지
