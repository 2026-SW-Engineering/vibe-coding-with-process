# 프로젝트 실험 설계 및 검증 지표 정리

쇼핑몰 주문 시스템은 겉보기엔 단순 CRUD 같지만, 실제로는 상태 불일치, 동시성 제어, 트랜잭션 처리가 얽힌 복잡한 도메인이다. 따라서 사전 설계나 명세 없이 프롬프트로만 개발하는 '바이브코딩'의 한계를 증명하기에 최적의 실험 주제다. 두 개발 방식의 차이를 정량적·정성적으로 비교하기 위한 관점과 실험 설계 방안을 아래와 같이 정리한다.

---

## 1. 비교 관점 및 지표

### A. 비용 및 리소스 관점 (정량 평가)

- **토큰 소모량 총합:** 프로세스를 준수하면 초기 설계에 토큰이 많이 들지만, 바이브코딩은 잦은 디버깅 핑퐁으로 누적 토큰 소모가 훨씬 클 것으로 예상됨. 개발 완료 시점까지의 총 누적 토큰량 비교.
- **프롬프트 핑퐁 횟수:** 에러 수정을 위한 반복 요청 횟수 및 소요 시간 비교.

### B. 아키텍처 및 코드 품질 관점 (정성/정량 평가)

- **모듈화와 관심사 분리:** 설계 없이 기능 구현만 지시할 경우, 하나의 파일에 UI, 비즈니스 로직, DB 접근을 모두 섞어버리는 '스파게티 코드(God Object)' 발생 여부 확인.
- **컨텍스트 유지력:** 코드 베이스가 커질수록 LLM이 이전 코드를 망각하거나 변수명을 임의로 변경하는 현상이 어느 트랙에서 더 자주 발생하는지 측정.

### C. 요구사항 및 예외 처리 견고성

- **Happy Path vs Edge Case 방어율:** 바이브코딩은 정상 흐름(Happy Path) 구현에는 빠르나 예외 처리에는 취약함. 사전에 정의한 엣지 케이스들을 얼마나 방어해 내는지 테스트 결과로 비교.

### D. 유지보수 및 확장성 관점

- **기능 추가 시 사이드 이펙트:** 기본 버전 완성 후 "포인트 적립 및 결제"라는 신규 요구사항 부여. 기존 결제/환불 로직이 망가지는지(바이브코딩), 아니면 기존 인터페이스에 맞춰 안전하게 확장되는지(소공 프로세스) 확인.

---

## 2. 주요 가설 및 검증 포인트

- **인간의 요구사항 분석 vs LLM 자동 추출:** LLM에게 요구사항 도출을 맡기면 일반적인 쇼핑몰 템플릿만 뱉어낼 확률이 높음. 정책적 예외 상황(부분 환불, 동시성 등) 도출에는 인간의 도메인 지식이 필수적임을 증명.
- **설계 부재와 코드 결합도:** 다이어그램이나 API 명세가 없으면 LLM은 컨텍스트 유지를 위해 인라인 코드로 길게 뽑아내는 경향이 있음. 사전 설계가 모듈 결합도를 낮추는 핵심임을 확인.
- **최소 요구 설계 수준 도출:** DB 스키마(ERD), API 스펙, 상태 머신 다이어그램 등 어떤 산출물을 제공했을 때 코드 품질이 가장 비약적으로 상승하는지 확인.

---

## 3. 실험 진행 프로세스 (A/B 테스트)

정확한 대조군 설정을 위해 두 트랙을 분리하여 진행한다.

### Track A (순수 바이브코딩)

- 사전 설계나 문서화 없이 자연어로 전체 기능 구현 요청. ("쇼핑몰 주문 시스템 만들어줘. 기능은...")
- 에러 발생 시 분석 없이 에러 로그만 복붙하여 수정 지시 반복.

### Track B (SW 공학 + LLM)

- 요구사항 명세, 시퀀스 다이어그램, ERD, API 스펙을 먼저 작성하고 확정.
- 확정된 설계 문서를 프롬프트 컨텍스트로 제공하며 모듈별로 코드 생성.
- 사전 정의된 엣지 케이스를 기반으로 테스트 코드 작성 및 검증.

---

## 4. 핵심 검증용 엣지 케이스 4선 (바이브코딩 붕괴 유도)

Track A 진행 시 아래 상황을 프롬프트에 명시하지 않고 개발을 유도한 뒤, 공통 테스트 케이스로 돌려 붕괴 현상과 복구 비용(토큰)을 측정한다.

### 1) 재고 동시성 문제 (Race Condition)

- **시나리오:** 재고 1개 남은 상품에 2명의 유저가 동시 결제 요청.
- **기댓값(소공):** 트랜잭션 1개만 성공, DB 락 기반 제어.
- **붕괴 포인트(바이브):** 단순 차감 로직(`stock - 1`) 적용으로 둘 다 결제 승인 후 재고가 음수 처리됨.

### 2) 가격 변동 및 검증 누락 (Price Tampering)

- **시나리오:** 장바구니에 담은 후 관리자가 단가 인상. 이후 유저가 예전 화면에서 그대로 결제 시도. (또는 API 결제 금액 변조)
- **기댓값(소공):** 결제 직전 최신 DB 단가 재조회 및 교차 검증 로직 작동.
- **붕괴 포인트(바이브):** 클라이언트가 보낸 과거 금액을 그대로 신뢰하여 오결제 발생.

### 3) 복합 조건의 부분 환불 (Complex State Mutation)

- **시나리오:** 조건부 할인 쿠폰 적용 결제 후, 묶음 상품 중 1개만 환불 요청.
- **기댓값(소공):** 쿠폰 적용 비율 안분 계산 혹은 조건 미달 시 쿠폰 할인액 회수 후 차액 환불.
- **붕괴 포인트(바이브):** 할인율 추적 스키마 미비로 원래 상품 단가를 100% 환불하여 회계적 손실 발생.

### 4) 결제 중복 요청 처리 (Idempotency)

- **시나리오:** 네트워크 지연 등으로 유저가 결제 버튼을 연속 클릭(따닥).
- **기댓값(소공):** 멱등성 키 또는 주문 상태 체크를 통해 첫 요청만 처리, 나머지는 무시.
- **붕괴 포인트(바이브):** API 중복 호출 방어 로직 부재로 PG사 결제 요청이 중복 발생하여 다중 출금됨.
