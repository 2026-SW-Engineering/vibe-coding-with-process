# 쇼핑몰 시스템 설계 문서 (정재 담당분)

> 범위: **클래스 다이어그램 · 시퀀스 다이어그램 · ERD** (+ 주문 상태 머신)
> 기준: 팀 요구사항 명세서(최종본). "무엇을"(요구사항) → "어떻게"(설계) 매핑.

## 1. 핵심 설계 결정 (Design Decisions)

요구사항에서 까다로운 지점들을 어떤 메커니즘으로 풀었는지 정리합니다. 다이어그램은 이 결정들을 시각화한 결과물입니다.

1. **주문 생명주기 = State 패턴.**
   상태 전이가 "단방향(역행 불가)"이고, 상태별로 가능한 동작(취소/환불)이 엄격히 다릅니다. `if(status == ...)` 분기를 서비스에 흩뿌리면 정합성이 깨지기 쉬워, 상태 자체를 객체(`OrderState`)로 만들어 **허용되지 않는 전이는 메서드 자체가 예외를 던지도록** 했습니다. (예: `ShippingState`에는 cancel/requestRefund 전이가 아예 없음)

2. **재고 동시성 = 비관적 락(SELECT ... FOR UPDATE) + 트랜잭션.**
   요구사항이 명시적으로 "DB 수준의 락 또는 트랜잭션"을 요구합니다. 충돌 빈도가 높은 재고 차감에는 낙관적 락(재시도 비용)보다 비관적 락이 안전합니다. 주문 항목별로 상품 row에 락을 걸고 → 재고 검증 → 차감 → 주문 생성을 **하나의 트랜잭션**으로 묶어 원자성을 보장합니다.

3. **가격 고정 = `OrderItem.confirmedPrice` 분리.**
   "주문 확정 가격은 이후 상품 가격이 바뀌어도 변하지 않는다"를 만족하려면, 주문 시점 가격을 `OrderItem`에 **스냅샷**으로 복사해야 합니다. 관리자의 가격 변경은 `Product.price`만 바꾸므로 기존 주문에 영향이 없습니다.

4. **장바구니는 가격 스냅샷을 보관하지 않음.**
   "장바구니에 담은 뒤 가격이 변경되면 장바구니 가격도 자연스럽게 바뀐다"가 최종 요구사항입니다. 따라서 `CartItem`은 수량만 갖고, 가격은 항상 `Product.price`를 참조합니다. 가격이 고정되는 시점은 **오직 주문 생성 시**입니다.

5. **환불 워크플로우 = 전체 취소(즉시) vs 부분 환불(승인 대기) 분리.**
   - 전체 취소: `결제완료`/`배송준비`에서만, **관리자 승인 없이 즉시** → 재고 복원, `취소완료`.
   - 부분 환불: `배송완료`에서만(7일 이내), **`환불요청` 상태로 대기** → 관리자 승인 시 부분 재고 복원 + `부분환불`, 거부 시 `배송완료`로 원복.
   두 경우 모두 `Refund` 엔티티로 기록하되 `type`으로 구분합니다.

6. **배송 시스템 = 외부 시스템(EIF).**
   `배송준비 → 배송중` 전이 시 외부 `DeliverySystem`에 출고 요청. 우리 시스템 경계 밖이라 클래스/시퀀스에서 `<<external>>`로 표기.

### ⚠️ 팀과 확인이 필요한 지점 (소연/태건에게)
- **`환불요청`을 "주문 상태"로 둘지** — 원래 enum 목록(`결제대기/결제완료/배송준비/배송중/배송완료/취소완료/부분환불`)엔 없지만, "거부 시 직전 상태(배송완료)로 복귀한다"는 문구는 주문이 `환불요청` 상태로 한 번 들어갔다 나온다는 의미라, 저는 **주문 상태에 `환불요청`을 추가**했습니다. (대안: 주문은 `배송완료` 유지하고 환불 상태만 별도 추적)
- **결제 시점 일부 품절 처리** — 장바구니 섹션("품절 항목 제외 후 알림")과 주문 섹션("재고 한도 내 성공/초과분 실패")이 미묘하게 다릅니다. 저는 **재고 부족 항목은 주문에서 제외 + 알림, 나머지는 정상 진행**(전부 제외되면 주문 실패)으로 통일했습니다.
- `재환불 불가`/`refundedQuantity`는 최종 스코프에서 빠졌지만(취소선), 정합성을 위해 필드는 남겨뒀습니다. 뺄지 결정 필요.

## 2. ERD

```mermaid
erDiagram
    USER ||--o| CART : owns
    USER ||--o{ ORDER : places
    USER ||--o{ REFUND : approves
    CART ||--o{ CART_ITEM : contains
    PRODUCT ||--o{ CART_ITEM : referenced
    ORDER ||--|{ ORDER_ITEM : contains
    PRODUCT ||--o{ ORDER_ITEM : referenced
    ORDER ||--|| PAYMENT : has
    ORDER ||--o{ REFUND : has
    REFUND ||--o{ REFUND_ITEM : contains
    ORDER_ITEM ||--o{ REFUND_ITEM : refunds

    USER {
        bigint id PK
        string email UK "시스템 내 유일"
        string password_hash "해시 저장(평문 금지)"
        string role "CUSTOMER | ADMIN"
        datetime created_at
    }
    PRODUCT {
        bigint id PK
        string name "상품명"
        int price "현재 판매가"
        int stock_quantity "재고 (항상 >= 0)"
        datetime created_at
        datetime updated_at
    }
    CART {
        bigint id PK
        bigint user_id FK "사용자당 1개(1:1)"
    }
    CART_ITEM {
        bigint id PK
        bigint cart_id FK
        bigint product_id FK
        int quantity
        datetime added_at
    }
    ORDER {
        bigint id PK
        bigint user_id FK
        string status "주문 상태"
        int total_amount "현재 결제액 = sum(확정가x수량) - sum(환불)"
        datetime ordered_at
        datetime delivered_at "환불 7일 기한 기준 시각"
    }
    ORDER_ITEM {
        bigint id PK
        bigint order_id FK
        bigint product_id FK
        int quantity
        int confirmed_price "주문 시점 확정가(고정)"
        int refunded_quantity "환불 누적 수량"
    }
    PAYMENT {
        bigint id PK
        bigint order_id FK "1:1"
        string status "SUCCESS | FAIL"
        int amount
        datetime paid_at
    }
    REFUND {
        bigint id PK
        bigint order_id FK
        bigint processed_by FK "승인/거부한 관리자"
        string type "FULL_CANCEL | PARTIAL"
        string status "REQUESTED | APPROVED | REJECTED"
        int refund_amount
        datetime requested_at
        datetime processed_at
    }
    REFUND_ITEM {
        bigint id PK
        bigint refund_id FK
        bigint order_item_id FK
        int quantity
        int refund_amount "확정가 x 환불수량"
    }
```

**제약/정합성 메모**
- `CART_ITEM(cart_id, product_id)` 복합 UNIQUE → 동일 상품 중복 담기 방지(수량으로만 증가).
- `stock_quantity >= 0` CHECK 제약.
- 전체 취소는 `REFUND(type=FULL_CANCEL, status=APPROVED)` 한 건으로 즉시 기록(개별 REFUND_ITEM 생략 가능).

## 3. 주문 상태 머신 (State Diagram)

State 패턴이 강제하는 전이 규칙을 그림으로. 화살표에 없는 전이는 **불가능**(메서드가 예외).

```mermaid
stateDiagram-v2
    [*] --> PAYMENT_PENDING : 주문 생성 (재고 차감)
    PAYMENT_PENDING --> PAID : 결제 성공
    PAYMENT_PENDING --> CANCELLED : 결제 실패 (재고 복원)
    PAID --> PREPARING : 관리자, 배송 준비
    PAID --> CANCELLED : 사용자, 전체 취소 (재고 복원)
    PREPARING --> SHIPPING : 관리자, 배송 시작 → 배송시스템
    PREPARING --> CANCELLED : 사용자, 전체 취소 (재고 복원)
    SHIPPING --> DELIVERED : 관리자, 배송 완료
    DELIVERED --> REFUND_REQUESTED : 사용자, 부분환불 요청 (7일 이내)
    REFUND_REQUESTED --> PARTIALLY_REFUNDED : 관리자 승인 (부분 재고 복원)
    REFUND_REQUESTED --> DELIVERED : 관리자 거부 (원복)
    CANCELLED --> [*]
    DELIVERED --> [*]
    PARTIALLY_REFUNDED --> [*]

    note right of SHIPPING
        배송중에는 취소도 환불도 불가
        (나가는 전이가 DELIVERED뿐)
    end note
```

> 한글 상태 매핑: PAYMENT_PENDING=결제대기, PAID=결제완료, PREPARING=배송준비, SHIPPING=배송중, DELIVERED=배송완료, REFUND_REQUESTED=환불요청, CANCELLED=취소완료, PARTIALLY_REFUNDED=부분환불

## 4. 클래스 다이어그램

레이어드 구조(Controller → Service → Repository → Domain) 중 **도메인 + State 패턴 + 핵심 서비스**를 표현합니다. (Spring Bean은 기본 싱글톤 → 비기능 요구사항의 "Singleton" 충족)

```mermaid
classDiagram
    %% ===================== Domain =====================
    class User {
        -Long id
        -String email
        -String passwordHash
        -Role role
        +isAdmin() boolean
    }
    class Role {
        <<enumeration>>
        CUSTOMER
        ADMIN
    }
    class Product {
        -Long id
        -String name
        -int price
        -int stockQuantity
        +decreaseStock(int qty) void
        +increaseStock(int qty) void
        +changePrice(int newPrice) void
    }
    class Cart {
        -Long id
        -User user
        -List~CartItem~ items
        +addItem(Product p, int qty) void
        +changeQuantity(Long itemId, int qty) void
        +removeItem(Long itemId) void
        +totalAmount() int
    }
    class CartItem {
        -Long id
        -Product product
        -int quantity
        +lineAmount() int
    }
    class Order {
        -Long id
        -User user
        -OrderState state
        -List~OrderItem~ items
        -int totalAmount
        -LocalDateTime deliveredAt
        +pay(PaymentResult r) void
        +prepareShipping() void
        +ship() void
        +completeDelivery() void
        +cancel() void
        +requestRefund(List items) Refund
        +recalcTotal() void
    }
    class OrderItem {
        -Long id
        -Product product
        -int quantity
        -int confirmedPrice
        -int refundedQuantity
        +lineAmount() int
        +refundableQuantity() int
    }
    class Payment {
        -Long id
        -PaymentStatus status
        -int amount
    }
    class Refund {
        -Long id
        -RefundType type
        -RefundStatus status
        -int refundAmount
        -List~RefundItem~ items
        +approve(User admin) void
        +reject(User admin) void
    }
    class RefundItem {
        -Long id
        -OrderItem orderItem
        -int quantity
        -int refundAmount
    }

    %% ============== State Pattern (Order) ==============
    class OrderState {
        <<interface>>
        +pay(Order o, PaymentResult r) void
        +prepareShipping(Order o) void
        +ship(Order o) void
        +completeDelivery(Order o) void
        +cancel(Order o) void
        +requestRefund(Order o, List items) Refund
        +status() OrderStatus
    }
    class PaymentPendingState
    class PaidState
    class PreparingState
    class ShippingState
    class DeliveredState
    class RefundRequestedState
    class CancelledState
    class PartiallyRefundedState

    OrderState <|.. PaymentPendingState
    OrderState <|.. PaidState
    OrderState <|.. PreparingState
    OrderState <|.. ShippingState
    OrderState <|.. DeliveredState
    OrderState <|.. RefundRequestedState
    OrderState <|.. CancelledState
    OrderState <|.. PartiallyRefundedState

    %% ===================== Service =====================
    class AuthService {
        +signup(String email, String pw) User
        +login(String email, String pw) Token
    }
    class ProductService {
        +list() List~Product~
        +changePrice(Long adminId, Long pid, int price) void
    }
    class CartService {
        +addToCart(Long userId, Long pid, int qty) void
        +updateQuantity(Long userId, Long itemId, int qty) void
        +viewCart(Long userId) Cart
    }
    class OrderService {
        +createOrder(Long userId, List itemIds, boolean paySim) Order
        +getMyOrders(Long userId) List~Order~
        +getOrderDetail(Long userId, Long orderId) Order
        +cancelOrder(Long userId, Long orderId) void
    }
    class PaymentService {
        +process(Order o, boolean simulateSuccess) PaymentResult
    }
    class RefundService {
        +requestPartial(Long userId, Long orderId, List items) Refund
        +approve(Long adminId, Long refundId) void
        +reject(Long adminId, Long refundId) void
    }
    class AdminOrderService {
        +advanceStatus(Long adminId, Long orderId) void
        +listAllOrders() List~Order~
    }

    %% ================== External (EIF) =================
    class DeliverySystem {
        <<external>>
        +requestShipment(Order o) void
    }

    %% ===================== Relations ===================
    User --> Role
    User --> "0..1" Cart
    Cart *-- "*" CartItem
    CartItem --> Product
    User --> "*" Order
    Order *-- "1..*" OrderItem
    OrderItem --> Product
    Order --> "1" Payment
    Order --> "*" Refund
    Refund *-- "*" RefundItem
    RefundItem --> OrderItem
    Order --> "1" OrderState

    OrderService ..> Order
    OrderService ..> PaymentService
    OrderService ..> ProductService
    RefundService ..> Refund
    AdminOrderService ..> Order
    PreparingState ..> DeliverySystem : ship 시 출고요청
```

**패턴 요약**
- **State**: `Order`는 동작을 현재 `OrderState`에 위임. 상태 클래스가 허용 전이만 구현 → 잘못된 전이는 예외.
- **Facade**: `OrderService`가 재고(`ProductService`)·결제(`PaymentService`)·주문 생성을 한 트랜잭션으로 조율.
- **Singleton**: 모든 Service/Repository는 Spring Bean(싱글톤).

## 5. 시퀀스 다이어그램

### 5-1. 주문 생성 + 결제 (재고 동시성 / 결제 성공·실패)

```mermaid
sequenceDiagram
    actor C as 고객
    participant OC as OrderController
    participant OS as OrderService
    participant PR as ProductRepository
    participant OR as OrderRepository
    participant PS as PaymentService
    participant DB as Database

    C->>OC: POST /orders (cartItemIds, 결제옵션)
    OC->>OS: createOrder(userId, itemIds, paySim)
    activate OS
    Note over OS,DB: 트랜잭션 시작
    loop 선택한 각 항목
        OS->>PR: findByIdForUpdate(productId)
        PR->>DB: SELECT ... FOR UPDATE (비관적 락)
        DB-->>PR: product(row lock)
        PR-->>OS: product
        alt 재고 < 요청 수량
            OS->>OS: 제외 목록에 추가 (품절/부족 알림 대상)
        else 재고 충분
            OS->>OS: confirmedPrice = product.price 로 고정
            OS->>PR: product.decreaseStock(qty)
        end
    end
    alt 확정 항목이 0개
        Note over OS,DB: 롤백
        OS-->>OC: 주문 실패(전부 품절)
        OC-->>C: 409 전 품목 품절 안내
    else 확정 항목 있음
        OS->>OR: save(Order = PAYMENT_PENDING)
        OR->>DB: INSERT order, order_item
        OS->>PS: process(order, 결제옵션)
        alt 결제 성공
            PS-->>OS: SUCCESS
            OS->>OS: order.pay(SUCCESS) → PAID
            OS->>OS: 장바구니 해당 항목 비우기
            Note over OS,DB: 커밋 (재고차감+주문+결제 원자적)
            OS-->>OC: order(PAID), 제외항목 목록
            OC-->>C: 201 주문 완료 (+ 제외 품목 알림)
        else 결제 실패
            PS-->>OS: FAIL
            OS->>OS: order.pay(FAIL) → 재고 복원 + CANCELLED
            Note over OS,DB: 커밋 (복원 반영)
            OS-->>OC: order(CANCELLED)
            OC-->>C: 200 결제 실패 안내
        end
    end
    deactivate OS
```

### 5-2. 부분 환불 요청 → 관리자 승인/거부

```mermaid
sequenceDiagram
    actor C as 고객
    actor A as 관리자
    participant RC as RefundController
    participant RS as RefundService
    participant OR as OrderRepository
    participant RR as RefundRepository
    participant PR as ProductRepository

    C->>RC: POST /orders/{id}/refunds (대상항목, 수량)
    RC->>RS: requestPartial(userId, orderId, items)
    activate RS
    RS->>OR: findById(orderId)
    OR-->>RS: order
    RS->>RS: 검증 (본인 / 상태=배송완료 / 7일 이내 / 수량<=주문수량)
    alt 검증 실패
        RS-->>RC: 예외 (권한/상태/기한)
        RC-->>C: 400 또는 403
    else 검증 성공
        RS->>RS: order.requestRefund(items) → REFUND_REQUESTED
        RS->>RR: save(Refund = REQUESTED)
        RS-->>RC: refund(REQUESTED)
        RC-->>C: 202 환불요청 접수 (승인 대기)
    end
    deactivate RS

    Note over A,PR: ===== 관리자 처리 =====
    A->>RC: PATCH /admin/refunds/{id} (APPROVE / REJECT)
    RC->>RS: approve(adminId, refundId) 또는 reject(...)
    activate RS
    RS->>RR: findById(refundId)
    RR-->>RS: refund
    alt 승인 (APPROVE)
        loop 각 환불 항목
            RS->>PR: product.increaseStock(qty)
            RS->>RS: orderItem.refundedQuantity += qty
        end
        RS->>RS: refundAmount = sum(확정가 x 수량)
        RS->>RS: order → PARTIALLY_REFUNDED, totalAmount -= refundAmount
    else 거부 (REJECT)
        RS->>RS: order → DELIVERED 로 원복
        Note over RS: 재고/금액 변경 없음
    end
    RS->>RR: save(refund = APPROVED 또는 REJECTED)
    RS-->>RC: 처리 결과
    RC-->>A: 200
    deactivate RS
```

> **전체 취소**(결제완료/배송준비 → 취소완료)는 위 부분환불과 흐름이 유사하나 **관리자 승인 단계가 없고**(즉시), 모든 항목 재고를 복원합니다. 상태 머신(3장)에 전이가 표현돼 있어 별도 시퀀스는 생략했습니다.

## 6. 요구사항 → 설계 추적표 (Traceability)

| 요구사항 | 설계 반영 |
|---|---|
