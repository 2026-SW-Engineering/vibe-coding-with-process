# 요구사항 분석

- 태건님 초안
    - 주문 시스템
        - 고객이 상품을 검색 → 장바구니 → 주문 → 결제 → 환불
    - Actor
        - Customer: 상품 검색, 장바구니 담기, 주문, 환불
        - Admin: 상품 등록, 재고 관리, 주문 처리
        - System: 결제 처리, 재고 차감, 상태 관리
    - 기능 요구사항
        - 상품 관리
            - 상품 조회
            - 상품 등록/수정
            - 상품 재고 조회
        - 장바구니
            - 장바구니 상품 추가
            - 장바구니 상품 수량 변경
            - 장바구니 상품 제거
            - 장바구니 조회(목록&총액)
        - 주문
            - 주문 생성(장바구니 → 주문 전환)
            - 주문 조회(자신의 주문 이력)
            - 주문 상태 관리(대기 → 처리중 → 완료)
            - 주문 취소(특정 상태에서만 가능)
        - 결제 & 환불
            - 결제 처리(가격 확정 & 결제)
            - 전체 환불(주문 전체 취소)
            - 부분 환불(일부 상품 환불)
            - 환불 이력 조회
    - 고려해야할 점
        - 재고 동시성 문제
        - 가격 변동 문제
        - 부분 환불 문제
        - 배송 상태에 따른 환불 불가 처리
        - 결제 실패 처리
        - 동일 상품 중복 장바구니 추가

# 액터

- 비로그인 사용자: 상품 조회만 가능
- 일반 사용자: 로그인한 사용자. 장바구니/주문/환불 가능
- 관리자: (최소한의 기능만 넣자) 상품 가격 변경, 주문 상태 변경, 환불 승인

# 기능 요구사항

- 회원/인증
    - 사용자는 이메일과 비밀번호로 회원가입할 수 있다. (이메일은 시스템 내 유일)
    - 사용자는 이메일과 비밀번호로 로그인
    - 비로그인 사용자는 상품 조회만 가능하고, 장바구니/주문/환불 기능은 사용할 수 없음
    - 사용자는 로그아웃할 수 있음
    - 사용자는 일반 사용자 또는 관리자 역할(role)을 가진다. 회원가입으로 생성되는 계정은 항상 일반 사용자이며, 관리자 계정은 시드 데이터로만 존재한다.
    - 관리자 전용 기능에 일반 사용자가 접근을 시도하면 시스템은 권한 거부로 응답해야 한다.
- 상품 조회
    - 모든 사용자는 등록된 상품 조회
        - 조회 시 표시될 항목: 상품명, 가격, ~~재고 잔여 여부~~
    - ~~사용자는 개별 상품의 상세 정보 조회~~
    - 상품 데이터 시드 데이터로 초기 적재
    - 일반 사용자는 상품 등록/삭제 할 수 없음
- 장바구니
    - 로그인한 사용자는 상품을 수량과 함께 장바구니에 담을 수 있다.
    - 사용자는 장바구니에 담긴 항목의 수량을 변경하거나 삭제할 수 있다.
    - ~~사용자는 자신의 장바구니 내용을 조회할 수 있으며, 조회 시점에 각 항목의 현재 가격과 담을 당시 가격이 다르면 시스템은 이를 사용자에게 명시적으로 표시해야 한다.~~
    - ~~결제 진행 시점에 장바구니 항목의 가격이 담을 당시와 다를 경우, 시스템은 결제를 자동 진행하지 않고 사용자에게 변경된 가격을 확인받은 후에만 결제를 진행한다.~~
    - 장바구니에 담아둔 후, 가격이 변경되면 장바구니에서도 자연스럽게 가격이 바뀐다.
    - 장바구니에서 표현된 가격으로 결제를 한다.
    - 장바구니에 담긴 시점에 재고가 있던 상품이 결제 시점에 품절된 경우, 시스템은 해당 항목을 결제에서 제외하고 사용자에게 알려야 한다.
- 주문/결제
    - 로그인한 사용자는 장바구니의 일부 또는 전체 항목을 선택하여 주문을 생성할 수 있다.
    - **주문 생성 시 시스템은 각 상품의 재고를 주문 수량만큼 차감한다.**
    - **재고 차감과 주문 생성은 원자적으로 처리되어야 한다.** 동일 상품에 대해 동시에 여러 주문이 발생하고 잔여 재고가 부족할 경우, 재고 한도 내에서만 주문이 성공하고 초과분은 실패 처리되어야 한다. (예: 재고 1개에 두 사용자가 동시 주문 시 정확히 1명만 성공)
    - 결제는 외부 PG 연동 없이 모의(mock) 처리하며, "결제 성공" 또는 "결제 실패"를 사용자가 선택하거나 시스템이 시뮬레이션할 수 있다.
    - 결제 실패 시 차감된 재고는 자동으로 복원되고 주문은 `취소완료` 상태로 기록된다.
    - 주문은 다음 상태 중 하나를 가진다: `결제대기`, `결제완료`, `배송준비`, `배송중`, `배송완료`, `취소완료`, `부분환불`. 정상 상태 전이는 `결제대기 → 결제완료 → 배송준비 → 배송중 → 배송완료` 순서를 따르며 역행할 수 없다.
    - 주문 총액은 각 항목의 (확정 가격 × 수량) 합계와 일치해야 한다.
- 주문 조회
    - 일반 사용자는 자신의 주문 내역 목록을 조회할 수 있다.
    - 일반 사용자는 자신의 개별 주문의 상세 정보(주문 항목, 수량, 항목별 확정 가격, 총액, 현재 상태)를 조회할 수 있다.
    - 일반 사용자는 다른 사용자의 주문을 조회할 수 없다.
    - 관리자는 전체 사용자의 주문 목록 및 상세 정보를 조회할 수 있다.
- 환불/취소
    - `결제대기 → 결제완료 → 배송준비 → 배송중 → 배송완료`
    - (취소)사용자는 `결제완료` 또는 `배송준비` 상태의 주문에 대해 전체 취소를 요청할 수 있다. 전체 취소 시 모든 항목의 재고가 복원되고 주문 상태는 `취소완료`로 변경된다. **전체 취소는 관리자 승인 없이 즉시 처리된다.**
    - (환불)사용자는 `배송완료` 상태의 주문에 대해 부분 환불을 요청할 수 있다. 부분 환불 시 환불 대상 항목과 수량을 지정할 수 있다. **부분 환불은 즉시 처리되지 않고 관리자 승인을 대기하는 `환불요청` 상태가 된다.**
        - 관리자가 부분 환불 요청을 승인하면, 환불 대상 항목의 수량만큼 재고가 복원되고, 환불 금액은 `해당 항목의 확정 가격 × 환불 수량`으로 계산된다. 주문 상태는 `부분환불`로 변경된다.
        - 관리자가 부분 환불 요청을 거부하면, 재고와 주문 금액은 변경되지 않고 주문 상태는 환불 요청 직전 상태(`배송완료`)로 복귀한다.
    - ~~부분 환불이 완료된 주문에 대해서도 추가 부분 환불 요청이 가능하다. 단, 이미 환불된 수량은 재환불 불가하다.~~
    - `배송중` 상태에서는 취소도 환불도 불가능하다.
    - `배송완료` 상태에서 환불 가능 기한은 배송완료 후 7일 이내로 한다.
    - !!! 배송시스템 → 우리 시스템과 소통하는 외부시스템 같은데, 이것도 다이어그램에서 보여주면 좋을 듯(EIF)
- 관리자 기능
    - **(상품 가격 변경)** 관리자는 등록된 상품의 가격을 변경할 수 있다. 가격 변경은 이후 시점부터 적용되며, **이미 확정된 주문의 항목 가격에는 영향을 주지 않는다. → 바이브코딩이 잘 할 수 있을지**
    - **(주문 상태 변경)** 관리자는 주문 상태를 정상 흐름에 따라 다음 단계로 전이시킬 수 있다 (`결제완료 → 배송준비`, `배송준비 → 배송중`, `배송중 → 배송완료`). 역행 전이나 단계 건너뛰기는 허용되지 않는다.
    - 관리자는 `환불요청` 상태의 부분 환불 요청을 조회하고 승인 또는 거부할 수 있다.

# 비기능 요구사항

- 데이터 정합성
    - 어떤 시점에도 상품의 재고 수량은 0 이상
    - `주문 총 결제 금액 = Σ(항목 확정가격 × 항목 수량) - Σ(환불 금액)` 성립
    - **주문에 기록된 항목별 가격은 주문 확정 시점의 가격으로 고정되며, 이후 상품 가격이 변경되어도 해당 주문의 항목 가격은 변하지 않는다.**
- 동시성
    - 동일 상품에 대한 동시 주문 요청에 대해서, 시스템은 **데이터베이스 수준의 락 또는 트랜잭션**을 통해 재고 초과 판매 방지
        - Singleton..
- 보안 및 권한 (추후 추가 가능)
    - 비밀번호 평문(x), 해시 저장(o)
    - 일반 사용자는 본인 데이터에만 접근할 수 있음
    - 관리자 전용 API는 관리자만 호출할 수 있어야
- 성능
    - 일반 사용자 요청(목록 조회, 장바구니 담기 등)은 3초 이내 응답
