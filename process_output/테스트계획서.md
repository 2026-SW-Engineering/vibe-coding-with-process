# **쇼핑몰 주문 시스템 — 테스트 계획서**

## **1. 개요 및 목적**

본 문서는 쇼핑몰 주문 시스템의 테스트 전략과 테스트케이스를 정의한다. 모든 테스트케이스는 요구사항 명세서 및 유스케이스 명세에서 도출되었으며, 두 개발 방식(SW 공학 프로세스 적용 vs 바이브코딩)의 결과물을 동일한 기준으로 비교·채점하는 채점표로도 사용된다.

**1.1 핵심 원칙**

- 테스트케이스의 기대값(expected)은 구현 코드(LLM 생성물)가 아니라 본 명세에서 도출한다. 구현은 LLM에게 위임하되, 무엇을 어떤 기대값으로 검증할지는 본 계획서가 규정한다.

- 롤백·동시성처럼 단위 테스트(mock 기반)로는 거짓 안심이 되는 항목은 통합 테스트 레벨에서 검증한다.

## **2. 테스트 레벨과 도구**

| **레벨** | **설명** | **도구** |
| --- | --- | --- |
| 단위 테스트 | 함수·메서드·클래스 단위를 격리 검증. 외부 의존성은 모킹. | JUnit 5, Mockito, AssertJ |
| 통합 테스트 | 여러 모듈이 DB와 함께 동작하는 흐름 검증(재고 차감, 결제 실패 롤백, 동시성). | @SpringBootTest, H2(인메모리) 또는 Testcontainers |
| 시스템 테스트 | 유스케이스 시나리오를 처음부터 끝까지 검증(E2E), 성능·보안 포함. | @SpringBootTest (MockMvc) |
| 인수 테스트 | 요구사항 명세를 기준으로 사용자 관점의 수용 여부 확인. | 유스케이스 시나리오 기반 검증 |

## **5. 시스템 / 인수 테스트**

| **유형** | **내용** |
| --- | --- |
| 기능 테스트 | 유스케이스 시나리오를 E2E로 검증(가입 → 로그인 → 장바구니 → 주문 → 출고 → 배송완료 → 부분환불). 인수 기준은 요구사항 명세서. |
| 성능 테스트 | 단순 조회 약 2초 이내, 주문 생성 약 5초 이내 응답. 동시 주문 부하 시 초과 판매가 발생하지 않음. |
| 보안 테스트 | 권한 우회 시도(타인 주문 조회, 관리자 API 무단 호출), 비밀번호 해시 저장 여부 확인. |

## **6. 구현(LLM) 지시사항**

구현은 LLM에 위임하되, 아래 지시에 따라 본 계획서의 테스트케이스를 코드로 옮긴다. 기대값은 본 문서를 기준으로 한다.

- 본 계획서 4장의 테스트케이스를 JUnit 5 기반으로 구현한다. 각 케이스의 기대값(기대 결과)은 반드시 본 문서를 기준으로 하며, 구현 코드의 동작에 맞추어 기대값을 수정하지 않는다.

- 경계값 케이스(TC-B06~B08 등)는 @ParameterizedTest로 묶어 작성한다.

- 서비스 계층 단위 테스트는 리포지토리·결제·배송 의존성을 Mockito로 모킹한다.

- 결제 실패 롤백(TC-S02)과 동시성(TC-C01~C03)은 단위(mock) 테스트로 대체하지 않고 @SpringBootTest 통합 테스트로 구현한다. 동시성은 ExecutorService로 실제 동시 요청을 발생시켜 검증한다.

- 테스트 커버리지는 JaCoCo로 측정하며, 두 개발 방식의 분기 커버리지를 동일 기준으로 비교한다.

## **7. 커버리지 측정 계획**

JaCoCo로 라인·분기 커버리지를 측정한다. SW 공학 프로세스 적용 버전과 바이브코딩 버전에 동일한 테스트 스위트를 적용하여 분기 커버리지와 예외 케이스 통과율을 비교하고, 그 차이를 비교 실험의 정량 지표로 사용한다.
